Arquitectura: cómo se organiza una aplicación completa

Arquitectura (de architecture) no es "qué hace el programa", sino dónde vive cada cosa y quién puede llamar a quién. Es el plano del edificio, no los muebles.

El problema que resuelve

Un programa pequeño cabe en un fichero. Pero en cuanto crece, aparecen cosas muy distintas mezcladas: leer un fichero, calcular una ruta, imprimir por pantalla, hablar con un navegador. Si todo está revuelto, cambiar una cosa rompe otras tres.

La analogía: una cocina de restaurante. El camarero (atiende al cliente), el cocinero (transforma ingredientes) y el almacén (guarda la comida) están separados a propósito. Si mañana atiendes pedidos por teléfono en vez de en mesa, cambias el camarero — la receta del cocinero no se toca.

Eso es exactamente lo que buscamos: que añadir una API web o una interfaz React no obligue a tocar el motor de simulación.

La regla de oro: hacia dónde apuntan las flechas

Las capas (layers) son anillos. Las dependencias solo apuntan hacia dentro: lo de fuera conoce lo de dentro, nunca al revés.

El dominio es el corazón y no importa nada de nadie: no sabe si hay ficheros, ni web, ni pantalla. Por eso es el trozo más estable y más fácil de testear.

Las capas clásicas, una por una

Capa 1

Dominio

Qué es el mundo. Las cosas que existirían aunque el programa no existiera: una zona, una conexión, un dron, y sus reglas (una zona blocked es intransitable).

Analogía: las reglas del ajedrez. Existen sin tablero físico ni app.

Capa 2

Aplicación

Qué sabe hacer el sistema. Orquesta el dominio para cumplir un caso de uso: "simula este mapa y dame las líneas de cada turno".

Analogía: el cocinero. Combina ingredientes siguiendo un procedimiento; no atiende mesas ni va al mercado.

Capa 3

Infraestructura

Cómo se habla con el mundo exterior. Leer texto, traducirlo a objetos, escribir en disco, consultar una base de datos. Es lo "sucio" y lo que más cambia.

Analogía: el almacén y los proveedores.

Capa 4

Presentación / Adaptadores

Quién pide las cosas y cómo se muestran. Un CLI, una API REST, una interfaz web. Cada uno es una puerta distinta al mismo motor.

Analogía: el camarero (o el repartidor, o la web de pedidos).

La prueba del algodón: si borras la capa de presentación entera, el sistema sigue teniendo sentido y los tests siguen pasando. Si borras el dominio, no queda nada.

Cómo se llama todo eso en Fly-In

Nuestras carpetas no se llaman "aplicación/infraestructura": se llaman por lo que hacen. Este es el mapeo real, carpeta a carpeta.

Capa clásicaCarpeta en backend/flyin/ Clase principalResponsabilidad
Dominio domain/ Zone, Connection, FlyInMap Qué es una zona, su tipo y su coste de movimiento. No sabe leer ni imprimir nada.
Dominio (transversal) shared/ MapParseError, UnsolvableMapError Tipos comunes que cualquier capa puede usar. No depende de ninguna otra.
Infraestructura parsing/ MapParser Traduce texto crudo → objetos de dominio, con errores por línea. Es la puerta de entrada de los datos.
Aplicación (núcleo algorítmico) graph/ Graph Convierte el mapa en adyacencia transitable (fuera las zonas blocked).
Aplicación (núcleo algorítmico) pathfinding/ Dijkstra, Path Ruta más barata sobre el grafo, y si el mapa es resoluble.
Aplicación (caso de uso) simulation/ Simulator El motor reusable: turno a turno, produce las líneas exactas de salida. No sabe quién lo llama.
Aplicación M4 scheduling/ por nacer Reservas de capacidad y tiempo cuando haya varios drones.
Presentación cli/ Cli + __main__.py Primer cliente del motor: fichero → simular → stdout; errores a stderr.
Presentación post-mandatory api/ (FastAPI) por nacer Segundo cliente del mismo motor: frontera REST (JSON).
Presentación post-mandatory frontend/ (React) por nacer Consume el JSON de la API y lo dibuja. Cero lógica de negocio.

Fíjate en un detalle que sí puedes defender: graph/ y pathfinding/ son algoritmos puros. En una app de gestión típica no existirían; aquí son el músculo del proyecto, por eso tienen carpeta propia en vez de esconderse dentro de simulation/.

El viaje de un mapa, de principio a fin

Esto es lo que ocurre hoy, de verdad, cuando escribes python -m flyin maps/map1.txt. Cada paso transforma un tipo de dato en otro.

1
Presentación · cli

__main__.py → Cli.run(argv)

Coge el nombre del fichero de los argumentos y lo lee del disco. Si no se puede leer: mensaje a stderr y código de salida 1.

argv: list[str] → text: str
▼
2
Infraestructura · parsing

MapParser(text).parse()

Analiza el texto línea a línea y construye los objetos. Si algo está mal, lanza MapParseError con el número de línea físico. A partir de aquí, nadie vuelve a ver texto crudo.

text: str → FlyInMap
▼
3
Aplicación · graph

Graph(fly_in_map)

Construye la adyacencia (quién es vecino de quién), dejando fuera las zonas blocked. Coste O(V + E).

FlyInMap → dict[str, set[str]]
▼
4
Aplicación · pathfinding

Dijkstra(graph, map).shortest_path()

Busca la ruta más barata de start a end. Devuelve un Path, o None si no hay ruta. Coste O((V + E) · log V).

Graph + FlyInMap → Path | None
▼
5
Aplicación · simulation

Simulator(fly_in_map).run()

El motor. Convierte la ruta en movimientos por turno y devuelve las líneas exactas que pide el subject. Si no hay ruta, lanza UnsolvableMapError.

FlyInMap → list[str] # ["D1-b", "D1-end"]
▼
6
Presentación · cli

Cli escribe el resultado

Imprime una línea por turno en stdout y devuelve 0. Los errores nunca contaminan stdout: van a stderr.

list[str] → stdout + exit code

La observación clave: los pasos 2–5 no saben que existe un terminal. No hay un solo print() en el motor. Toda la entrada/salida está encerrada en el paso 1 y el 6.

Ese encierro es lo que llamamos una costura (seam): el punto por donde puedes enchufar otra cosa sin romper nada.

La foto global: un motor, muchas puertas

Este es el objetivo final del proyecto completo. El mismo Simulator del centro, con tres clientes distintos.

Los tres clientes llaman al mismo código. La API no reimplementa la simulación: la envuelve. El frontend no calcula rutas: pinta lo que la API le devuelve.

Por qué esto se llama "puertos y adaptadores"

Un puerto (port) es la forma del enchufe que el núcleo ofrece: "dame un FlyInMap, te devuelvo una list[str]". Un adaptador (adapter) es lo que se enchufa ahí: el CLI, la API, un test.

Analogía: el enchufe de la pared (puerto) es siempre igual; la lámpara, el cargador o la tostadora (adaptadores) cambian. La pared no se entera de qué has enchufado. Por eso la decisión del 2026-08-12 fue que el mapa entra como fichero-argumento en el CLI, pero el motor recibe texto/objetos: cambiar la fuente no toca el núcleo.

Qué gana el proyecto con esto (y qué cuesta)

Testeable

Puedes testear Dijkstra sin ficheros, y el Cli sin lanzar un proceso (por eso los flujos se inyectan en el constructor).

Sustituible

Cambiar Dijkstra por A* toca una carpeta. Añadir la API no toca ninguna de las existentes.

Explicable

En la defensa puedes recorrer el camino del dato en 6 pasos y señalar el fichero exacto de cada uno.

El coste (sé honesto)

Más carpetas y más indirección para un programa que "solo imprime líneas". Se justifica porque el subject pide OOP y porque las extensiones están decididas — no porque sí.

Riesgo de defensa que debes tener preparado

Un evaluador puede decir: "¿no es sobreingeniería tener 7 carpetas?". La respuesta honesta, y que además es cierta en este repo:

"Ninguna carpeta nació de forma especulativa: cada una nació en el slice en el que el código la justificó, y está registrado en docs/PROGRESS.md con la fecha y el motivo. scheduling/, api/ y visualization/ todavía no existen precisamente por eso."

Glosario

TérminoQué significa
Arquitectura Cómo se reparte el código en piezas y qué pieza puede llamar a cuál.
Capa (layer) Grupo de código con una responsabilidad del mismo nivel (dominio, aplicación…).
Dominio Las entidades y reglas del problema en sí, sin tecnología alrededor.
Dependencia Que un fichero necesite (importe) a otro para funcionar.
Acoplamiento (coupling) Cuánto depende una pieza de otra. Poco acoplamiento = cambiar una no rompe la otra.
Adaptador (adapter) Pieza fina que traduce entre el mundo exterior y el núcleo. El Cli es uno.
Puerto (port) La "forma del enchufe" que el núcleo ofrece: qué recibe y qué devuelve.
Costura (seam) Punto del código pensado para poder enchufar algo distinto sin reescribir.
Motor / núcleo (engine, core) El código que resuelve el problema de verdad, sin saber quién lo llama.
Inyectar (dependency injection) Pasarle a una clase lo que necesita (p. ej. los flujos de salida) en vez de que se lo busque ella.
stdout / stderr Los dos canales de salida de un programa: el resultado y los mensajes de error, separados.
REST / API Forma estándar de que un programa pida cosas a otro por la red, normalmente con JSON.
Backend / Frontend La parte que calcula (servidor) y la parte que se ve (navegador).

Resumen en una frase para la defensa:

"El proyecto está en capas con las dependencias apuntando hacia dentro: el dominio no sabe nada de nadie, el parser traduce texto a dominio, el grafo y Dijkstra calculan rutas, el simulador es un motor reusable que no sabe quién lo llama, y el CLI es un adaptador fino de 60 líneas. Por eso una API o una UI se añaden como clientes nuevos sin tocar el motor."
